# Правила ведения проекта MyGoods

Документ описывает, как команда работает с репозиторием: ветки, коммиты, pull request'ы и связь с доской Kaiten.

## 1. Ветки

| Ветка                               | Назначение                                                                     | Кто пушит |
| ----------------------------------- | ------------------------------------------------------------------------------ | --------- |
| `main`                              | Стабильная версия. То, что показываем на демо и выкладываем на тестовый сервер |
| `develop`                           | Общая рабочая версия. Сюда сливаются все готовые задачи                        |
| `<номер "краткое описание задачи">` | Ветка под одну задачу из Kaiten                                                |

### Название ветки

Формат: `<номер-краткое-описание-задачи>` пример `<1-warehouse-management-forms>`

Номер задачи берём из документа спринта и Kaiten. Назвние на английском

## 2. Работа над задачей

### Шаг 1. Взять задачу

В Kaiten перенести карточку в **In progress**

### Шаг 2. Создать ветку от свежего `develop`

```bash
git checkout develop
git pull origin develop
git checkout -b 1-warehouse-management-forms
```

### Шаг 3. Писать код и коммитить

Коммиты делаем небольшими: один коммит — одно логическое изменение

Формат сообщения: `<номер задачи>: <что сделано>`, на русском

```bash
git add .
git commit -m "1: добавить таблицу товаров в каталог"
```

### Шаг 4. Перед PR подтянуть свежий `develop` в свою ветку

Конфликты решаем у себя в ветке, а не в `develop`.

```bash
git fetch origin develop:develop
git merge develop
```

`git fetch origin develop:develop` обновляет локальный `develop`, не переключаясь на него. Команда работает, только когда ты находишься на своей ветке, а не на `develop`.

Если появились конфликты:

1. Решить конфликт
2. Проверить, что проект собирается и запускается
3. Закоммитить слияние (со стандартным сообщением слияния)

### Шаг 5. Проверить перед отправкой

- Проект собирается и запускается.
- Фронт: `npm run lint` и `npm run build` проходят без ошибок.
- Бэк: `dotnet build` проходит
- В коммитах нет лишнего: `node_modules`, `bin`, `obj`, `.env`, личные настройки IDE.

### Шаг 6. Отправить ветку и открыть PR

```bash
git push -u origin 1-warehouse-management-forms
```

## 3. Pull Request

### Как открыть PR

1. Открыть репозиторий на GitHub.
2. Перейти на вкладку **Pull requests** → нажать **New pull request**.
3. Выбрать ветки:
   - **base:** `develop` — куда сливаем;
   - **compare:** `1-warehouse-management-forms` — твоя ветка, откуда сливаем.

   Проверь, что в **base** стоит именно `develop`, а не `main`.

4. Посмотреть список изменений внизу страницы: там должны быть только файлы твоей задачи.
5. Нажать **Create pull request**.
6. Заполнить название (номер и название задачи как в Kaiten)
7. Справа в **Reviewers** выбрать ревьюера.
8. Нажать **Create pull request**.

## 4. Что нельзя коммитить

- Пароли, токены, строки подключения к реальным базам. Для этого есть `.env` (он в `.gitignore`) и `.env.example` с пустыми значениями.
